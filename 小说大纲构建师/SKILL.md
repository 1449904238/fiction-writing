# 小说大纲构建师

把设定转化为能持续制造选择、代价和新问题的故事计划。优先保障人物因果、主题兑现、读者承诺和连续性；格式服务于写作，不能用表格数量替代戏剧质量。

## 输入与边界

本 skill 独立运行：输入只有一份小说设定，输出直接是这份大纲。不要假设上游或下游流程，不要要求用户提供其他 skill 的产物。

典型输入是 `_设定架构.md` 样式的设定文档，通常包含：定位与读者承诺、人物因果链、世界规则/地点/势力、题材引擎、连续性账本和反模板约束；也可以接受等价的设定材料，或 `设定包/`（`manifest.json` + `01_设定元数据.json` + `02_写作约束.json`，有则直接读取；`.work/core_gate.json` 与 `00_创作简报.md` 是额外的质量输入，一并读取）。两者都不存在时，先收集：主角此刻必须解决的困境、主角目标、读者应反复获得的体验、预期篇幅或平台。

消费 `设定包/` 时要**忠实传递**它的线索账本与写作约束，不是参考：`clue_ledger` → `foreshadowing`（用 `source_clue` 绑定），`narrative_guardrails.avoid_moves/required_moves` → `genre_profile.avoid_moves/must_deliver`，`.work/core_gate.json` → `direction_gate`，`02` 的 `scene_test` → `gocs/state_delta`。完整字段映射见 [references/大纲数据契约.md](references/大纲数据契约.md) 的「设定包 → 大纲 字段映射」表；`validate --setting-package <目录>` 会对映射做机检。

《雾港档案》的示例设定包（`../小说设定架构师/示例_设定包/`，悬疑题材四件套）只是输入形状示例，不是绑定内容：对任何同形状的设定文档都必须成立，题材、人物与规则全部取自实际输入的设定，不得因为示例本身而默认复用这一套题材和角色。

从设定中提取并按原样保留：角色名、目标、底线、关系、规则、地点、势力、资源、不可逆事实和结局意图。明确标注哪些是“新增推导”，把会阻塞大纲的缺失写进 `open_decisions`（每项含 `question`、`blocks`、`owner`），不要在缺失项上伪造设定。不要虚构榜单、平台政策、阅读数据或对标原文；没有可靠材料时，把节奏要求标为 `editorial_assumption`。

缺少主角困境、主角目标、读者承诺中两项以上时，不要伪造完整大纲；给出三个差异明显的高概念种子，请用户选择。

默认目标是长篇中文网文。短篇、系列、特定平台、既有大纲和用户明确的风格要求优先于默认节奏。不要把成长/战斗题材的能力等级套用到言情、悬疑、历史或现实题材。

## 工作流

### 执行模式与停机条件

每次任务先声明一个模式，不得跳过方向闸门直接生成全书：

| 模式 | 产出 | 放行条件 |
|---|---|---|
| `MODE_DIRECTION` | `direction_gate` + 3 个开局交付 | 读者承诺、卖点和前三章冲突均可写；否则停在此模式 |
| `MODE_ENGINE` | `story_engine` + `setting_refs` | 主角、对手、升级梯和终局证明均有因果证据 |
| `MODE_VOLUMES` | 分卷骨架 + 叙事线/伏笔/分支计划 | 卷间存在“结果→新限制→新目标”链 |
| `MODE_CHAPTER_BATCH` | 每批 3-5 章 + 投影交接 | 本批 JSON 通过校验后才开始下一批 |
| `MODE_REPAIR` | 只修复审计失败项 | 不得借修复改写用户已锁定事实 |

默认使用 `MODE_CHAPTER_BATCH`，批次上限 5 章；用户明确要求全书时仍须分批生成、分批验证，不一次性倾倒整书。

每次先锁定 `genre_profile.primary`，只使用该题材对应的推进轴和禁用替代动作。长篇生成必须维护 `story_threads`；每章的 `state_delta` 和 `thread_ops` 是下一批的入口状态，不能只靠回忆上一批文字。

连续性账本的默认规则是：下一章 `entry_state` 至少承接上一章的一个 `changed_state` 或 `new_obligations`。确有时间跳跃、视角切换或状态重置时，才使用 `continuity_break=true`，并写明 `continuity_note`；不能用它掩盖漏接。

### 1. 建立创作决策

先完成 `direction_gate`，通过后才能展开：

- 一句话前提：谁在什么失衡处境中，为什么现在必须行动。
- 读者承诺：读者会反复获得的体验，而非题材标签。
- 卖点：`谁 + 独特困境 + 非常规手段/资源 + 反预期结果`。
- 目标读者与阅读场景：基于用户材料或明确标为创作假设，避免性别刻板印象。
- 对标：仅使用用户提供、已拆解或可核实的作品；记录借鉴的功能和差异化边界，不复制情节。
- 开局兑现：首 500 字、前三章各自可写的冲突、回报或威胁。

检查：读者承诺是否能在前三章被看见；卖点能否用一句口语转述；核心冲突能否持续反制主角。任一为否时，重做本步骤。

### 2. 建立故事引擎

为主角、主要对手和终局建立可验证的因果链：

- 主角：外在目标、内在误判/缺口、底线、资源、可失去之物、压力下的可观察行为。
- 对手：目标、可调用资源、主动计划、每次受挫后的升级策略，以及与主角价值选择的冲突。
- 主题命题：故事要检验的价值冲突，不写空泛口号。
- 终局证明：终局中主角必须作出的不可逆选择，以及它如何回答主题命题。
- 升级梯：至少三次性质不同的升级；每次都改变信息、关系、能力、资源或代价中的至少一项。

不要只列“角色从 A 到 B”。必须写清导致变化的压力、选择、代价和新行为。对悬疑使用证据与认知升级；对言情使用关系边界与信任交换；对成长/战斗题材才使用能力阶梯。

### 3. 规划分卷因果骨架

每卷都要回答：本卷承诺什么体验、主角要什么、谁以什么方式阻止、主角做了什么选择、付出了什么不可逆代价、卷末状态为何迫使故事进入下一卷。

以因果链而非事件串连接各卷：`前卷结果 -> 新限制/新信息 -> 新目标 -> 更难选择`。为每卷标出 1/4、中点、3/4 和卷末的功能锚点，但根据卷长动态计算，不强制十章一卷。

为每个关键场景写 GOCS 卡：

- `Goal`：视角角色要得到什么。
- `Obstacle`：具体谁或什么阻止它。
- `Choice`：角色采取何种有代价的行动。
- `State change`：结果如何改变人物、关系、资源、信息或局势。

仅为确实独立的叙事线建立 `narrative_lines`。章节可同时推进多线，因此“比例”按场景/节拍权重计算，不将交汇章节重复计入总和。单线故事不强行切副线；多线故事须有交汇、回归主冲突和可解释的切换理由。

### 4. 制定伏笔、反转与分支

为每条伏笔分配 `FS-XXX` ID、类型、重要度、埋设、推进、预期回收区间、回收方式与关联伏笔。伏笔不是谜语清单：其回收必须改变角色选择或故事理解。

关键选择、转折或危机才做分支推演。每个节点保留一个选定分支和至多两个备选分支；选定分支必须包含短期、中期、长期后果及风险。备选分支只保留真正不同的故事走向，不保存“同一路线更顺利/更曲折”的伪分支。

反转必须有可回溯的前置证据、当下的因果解释和反转后的消化空间。禁止靠隐藏关键事实、临时天降资源或角色突然失智制造反转。

### 5. 逐批规划章节

默认先交付首卷或首 10 章，再根据用户反馈继续；只有用户明确要求全书逐章计划时才一次输出全部章节。每章写清：章节目标、叙事线、GOCS、目标读者情绪、场景效果、节奏功能、伏笔操作和章末的“继续阅读理由”。

新生成的大纲声明 `contract_version = "1.3"`，并为每章写 `axis_advance`：轴名必须落在题材词表内（见 `genre_contracts.json`），写明本次推进的 `change` 与 `cost_paid`；休整章用 `axis=休整` 且 `delivers` 逐字兑现一条 `must_deliver`。关键实体（有状态会死亡/销毁/易主的）记入 `entity_ledger`。续批时声明 `chapter_offset` 与 `inherited`（承接上一批的线程/伏笔 ID），并用 `finalize --previous` 核验衔接。

钩子可以是未完成的行动、代价、选择、关系变化或新问题，不必每章使用悬念句式。低压章允许没有显性爽点，但必须兑现关系、信息、世界、休整或伏笔中的至少一种功能。目标平台明确时填 `commercial_profile`；有真实对标数据用 `benchmarked + evidence_source`（指向真实文件），否则诚实声明 `editorial_assumption`，禁止虚构来源。

### 6. 审计并交接

先执行下列检查，再输出最终资产：

- 所有角色、地点、势力、资源和既有伏笔引用都存在，且遵守上游连续性约束。
- 每卷有独立目标、代价和状态变化；全书升级梯通向终局证明。
- 每个核心场景都有 GOCS；每个重大转折有前置依据。
- 章节区间无缺口或重叠；叙事线权重可解释；交汇章节记录所有推进线。
- 伏笔 ID 唯一，回收不早于埋设，P0 伏笔有明确回收或弃用决策。
- 情绪不是只用“高/中/低”标记：同时记录具体体验和节奏功能，二者不得混用。
- `open_decisions` 未包含会使后续写作自相矛盾的未决问题。

将机器资产保存为 `01_大纲数据.json`（纯对话且用户不需要机器资产时可以省略，但仍须先在文本中完成同等检查）。只要生成 JSON，就统一运行 `scripts/finalize_outline.py 01_大纲数据.json --skip-handoff`：它执行版本/语义校验、写连续性账本与 `03_审计回执.json`，并跳过 `02_细纲交接` 投影。关于 `--skip-handoff`：`finalize_outline.py` 默认会产出 `02_细纲交接`（可选投影，下游细纲构建的消费格式），加 `--skip-handoff` 才不产出；本 skill 只交付大纲，故统一加该标志，仅在确有明确的下游细纲消费者请求时才去掉它重新运行。续批时追加 `--previous <上一批输出目录>` 触发跨批核验（章节衔接、线程/伏笔承接、实体终态、版本不降级）。没有 `status=passed` 的审计回执，不得交付或声称已完成；校验失败进入 `MODE_REPAIR`，不以"后续再补"放行。

回执中的 `WARN` 项是分级门禁的质量路由：机检不拒绝，但必须按 [references/judge_protocol.md](references/judge_protocol.md) 做语义评审抽查，评审产出的判断文件用 `scripts/verify_judgment.py` 核验证据锚点后才作数。没有评审结论时，warn 只能如实转述，不得宣称“已确认无问题”。

`03_连续性账本.json` 是内部派生保障与跨批核验依赖（含 `--previous` 续批），在任何模式下始终由 finalize 写出。`02_细纲交接.json/.md` 是 `finalize_outline.py` 的**可选投影、下游细纲构建的消费格式，非本 skill 的常规产出**：不带 `--skip-handoff` 运行时 finalize 会生成它，带该标志则跳过；本 skill 默认带标志运行（只交付大纲），去掉标志即表示按明确的下游细纲消费者请求产出交接。投影文件是派生物，不得手工修成另一套事实。

可用 `python evals/run_evals.py examples --report evals/report.json` 做结构烟雾评测；`python evals/run_evals.py --self-test` 一键运行全部对抗回归套件（题材契约 block/warn 分级、商业层机检、语义评审证据核验、跨批负例与正例链路、1.2 兼容回归）。质量盲评按 [evals/quality_rubric.json](evals/quality_rubric.json) 和 [evals/review-template.md](evals/review-template.md) 记录，再用 `python evals/aggregate_reviews.py REVIEWS_DIR` 汇总。评测报告中未测的质量项必须保持 `unmeasured`，不得填入推测百分比。

### 执行率记录

每批在交付说明中记录五个可复核分项：`R_input`（设定引用完整，且“保留/新增推导/未决项”可区分）、`R_schema`（Schema 通过）、`R_semantic`（语义校验通过）、`R_gate`（finalize 审计回执通过）、`R_quality`（人工故事质量盲评）。主要指标是 `E2E_pass_rate`（一个批次里全部确定性门禁通过的样本占比）；`R_quality` 和 `R_total` 没有独立盲评样本时标为 `unmeasured`，不得用脚本通过率冒充精彩度。

## 交付物

本 skill 是**独立的、只产出大纲**的流程：交付大纲本体与质量凭证，不产出细纲交接或其他下游内容。在可写入项目目录时交付以下资产；纯对话中按相同顺序输出。

1. `00_大纲简报.md`：给作者阅读。简洁说明方向、读者承诺、故事引擎、分卷因果、关键人物弧和未决项。
2. `01_大纲数据.json`（可选机器权威）：严格遵守 [大纲数据契约](references/大纲数据契约.md)，不使用占位符；生成就必须通过 `finalize_outline.py`。
3. `03_审计回执.json`（质量凭证）：`finalize_outline.py` 写出，证明各门禁通过；无 `status=passed` 不得交付。
4. `03_连续性账本.json`（内部保障）：连续性派生，供跨批核验保证一致性；不在交付物里强推。
5. `02_细纲交接.json/.md`（`finalize_outline.py` 的**可选投影**，下游细纲构建的消费格式，非本 skill 的常规产出）：默认不产出——本 skill 交付时统一用 `finalize_outline.py --skip-handoff` 运行；仅当存在明确的下游细纲/扩写消费者请求时，去掉 `--skip-handoff` 重新运行才会生成。未产出时在简报中注明"细纲交接属下游细纲构建，本 skill 已交付大纲"。

输出后简要列出：已验证项、新增推导、创作假设、`open_decisions` 和下一批建议规划的章节。不要在最终资产中输出自评打分、历史版本日志或无依据的"市场验证"结论。
